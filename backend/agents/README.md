# Admin AI agent — folder guide

## Layout

```
backend/
├── agents/
│   ├── admin_agent.py          # supervisor: plans, then runs SQL/Excel/Email/Instagram
│   ├── admin_sql_agent.py      # langgraph SQL subgraph (schema -> generate -> validate -> execute -> answer)
│   ├── agent_state.py          # TypedDict for the SQL subgraph state
│   ├── excel_export.py         # builds .xlsx from query rows (in-memory + save-to-disk)
│   ├── services/
│   │   ├── approval_service.py # in-memory pending-approval queue (email/instagram)
│   │   ├── email_service.py    # SMTP sender, used after an email is approved
│   │   └── instagram_service.py# Meta Graph API call — STILL A STUB, see below
│   └── tools/
│       ├── email_generator_tool.py     # drafts email subject/body via LLM
│       ├── instagram_generator_tool.py # drafts caption/image_prompt via LLM
│       ├── image_generator_tool.py     # turns image_prompt into an actual image via OpenAI images API
│       └── instagram_publish_tool.py   # gate: raises unless approved=True, then calls instagram_service
└── api/
    └── admin_api_chatbot.py    # FastAPI router: /ask, /ask/export, /download, /approve, /reject
```

## Still needs your input before this is production-ready

- **`instagram_service.py`** — `publish_post()` is a stub that fakes a
  "published" response. Wire in the real Meta Graph API call (create
  media container -> publish) with your IG business account id and a
  long-lived access token.
- **`email_service.py`** — needs SMTP env vars set:
  `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`,
  `SMTP_FROM_EMAIL`, `SMTP_USE_TLS`.
- **`image_generator_tool.py`** — needs `OPENAI_API_KEY` available to
  the `openai` client (same key your `ChatOpenAI` calls already use).
  If image generation fails, the Instagram approval still goes
  through with `image_url: null`; supply one manually via
  `POST /admin/approve/{id}?image_url=...`.
- **`approval_service.py`** — in-memory store. Fine for one dev
  process; will not survive a restart or work with multiple API
  workers. Swap the dict for a real table
  (`id, action_type, payload, status, created_by, created_at,
  decided_at`) when you move past local dev — the public method
  signatures were written so that swap doesn't touch calling code.
- **`AGENT_DATABASE_URL`** — required by `admin_sql_agent.py` to
  connect to your Postgres banking DB.

## Removed (dead, unused)

`tools/campaign_tool.py`, `tools/excel_tool.py`, `tools/sql_tool.py`
were empty stubs nothing imports — not included here. Re-add them
only if you plan to refactor into a true LangChain `Tool`-calling
ReAct agent instead of the current deterministic plan-then-execute
flow.

## New API endpoints

- `POST /admin/ask` — main entry point, plans + runs SQL/Excel/Email/Instagram
- `POST /admin/ask/export` — same, but returns rows as a downloadable .xlsx
- `GET  /admin/download/{filename}` — serves a report generated by `/ask`
- `GET  /admin/approvals/pending` — list everything waiting on a human
- `GET  /admin/approvals/{id}` — check one approval's status
- `POST /admin/approve/{id}` — approve + actually send/publish
- `POST /admin/reject/{id}` — reject, nothing gets sent
